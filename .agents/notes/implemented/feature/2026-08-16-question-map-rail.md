# Agent Note: QuestionMap — left-edge minimap rail over long transcripts

Status: implemented

English | [中文](2026-08-16-question-map-rail.zh.md)

## Problem

Long conversations make revisiting an earlier question tedious: the reader has to scroll the whole transcript and visually scan for the question. There was no overview of where questions sit in the flow and no shortcut to jump to one.

## Decision

A client-only minimap rail on the left edge of the transcript scrollport (`ui-conversation`'s `ChatView`):

- **Data**: `ChatView` projects one `QuestionMapEntry` per `user` or `steering` Chat Node, in flow order — assistant, tool, context, and lifecycle nodes are not questions. The tooltip label is the message's joined text blocks, whitespace-collapsed, trimmed, capped at 180 characters; an image-only question falls back to a localized `[图片消息] / [Image message]` label.
- **Geometry**: the rail is `position: fixed` and re-anchors off the scrollport's rect on every measure (left + 8; top + 16 for the reading area, whose height is clientHeight − `--dsh-composer-height` − 16). Fixed, not sticky, for the same reason the Tooltip primitive is fixed: the conversation column's active phase sets `overflow: hidden` on the root, and sticky would lose its scrollport under a composer-overlay view mode (`[data-conversation-composer-overlay]` clips the view area). The codebase already guarantees no transformed ancestor, so fixed never traps against a containing block.
- **Bars**: the bars are packed into a tight cluster — each is a 7px hit area (11×3 mark) at `index × 9px` from the cluster top, 2px apart — and the cluster is vertically centered in the reading area, so the rail stays a compact index no matter how long the transcript grows. The bar at the reading edge (the last question whose row top ≤ scrollport top + 16) is marked in business blue; the others are neutral. Hover is a visible state change: the mark stretches to the full bar width and brightens while the hit area fills with the interactive hover tint behind it (reduced-motion keeps the transition off). Hover also shows the question text in a `Tooltip` (side right, 150ms delay); click jumps the transcript so the question row lands 16px below the scrollport top — the jump is a viewport-relative `scrollTop` increment (`row top − scrollport top − 16`), which lands correctly from any scroll position, and `ChatView`'s existing scroll listener re-derives follow ownership and the saved reader position, so no ledger coupling was needed. The rail shows a fixed 10 bars at most (`RAIL_MAX_BARS`): a taller cluster becomes its own scroll container — scrollbar hidden, `pointer-events: auto` so wheel input scrolls it, with scroll chaining to the transcript at the edges — and a layout effect keeps the active bar in view, so the whole conversation stays reachable inside a bounded rail and the "you are here" mark stays visible.
- **Visibility gates**: the rail renders only when the session holds at least two questions AND the transcript actually scrolls (`list.scrollHeight > scrollport.clientHeight + 8`) AND the viewport leaves room above the composer. One scroll listener (drives the active marker; the rail's own geometry is scroll-invariant) plus one `ResizeObserver` on the scrollport and the flow list (drives re-anchoring on resize, header collapse, streaming, and paging). No listeners attach while the rail is hidden; both effects re-run when an entries change revives them.
- **Full-history coverage**: `ChatView` background-pumps older history until nothing remains (`hasMore && !loadingOlder → loadOlder()`, re-armed by the snapshot flip after each page), so the rail's entries always span the complete conversation — a fresh open of a long session no longer shows only the tail window's questions until the reader manually pages up. The pump is one page at a time (the runtime's in-flight guard), stops at `hasMore === false` or a failed page, and self-corrects across reconnect/resync, which reset the window and re-arm it.
- **Cost discipline**: the measure pass reads rects only for question rows (never all rows); `ChatView`'s render-economics and scroll-ownership logic are untouched — the map is a sibling component with its own refs (`listRef`; the scrollport is resolved per measure via `closest('[data-conversation-scroll]')`, and the rail keeps its own `railRef` for the overflow follow).

## Alternatives considered

**Sticky zero-size seat instead of fixed.** Rejected: sticky is relative to the nearest scroll container, and the conversation root's active-phase `overflow: hidden` plus the composer-overlay view mode would break it exactly when the transcript is scrolled (the composer seat works only because it is a direct scrollBody child). Fixed positioning with per-measure anchoring is the same technique the Tooltip primitive already uses in this codebase.

**Proportional placement instead of a packed cluster.** The initial implementation put each bar at the question's proportional place in the flow (`(rowTop − listTop) / list.scrollHeight`). Rejected after review: the user asked for a compact index — bars packed together and vertically centered — and proportional spread makes the rail as tall as the transcript and re-flows on every growth. The packed cluster stays a small control, and the reading-edge marker plus click-to-jump still carry the position and navigation semantics; a cluster that outgrows the fixed 10-bar rail length scrolls inside it instead of stretching.

## Consequences

Long conversations get a one-glance question index and one-click navigation; the rail appears only when it is useful (≥ 2 questions, scrollable transcript), so short chats stay uncluttered, and it stays a fixed-size control on long ones — a cluster beyond 10 bars scrolls inside the rail by wheel instead of growing to screen height. New coverage: `question-map.client.spec.tsx` (projection, packed-cluster placement, active marker, hover, jump, visibility gates, fixed-cap and overflow-follow geometry, listener lifecycle) and the chat-view pump test (background paging, no concurrent pages, stop at exhaustion). No host changes; the feature is pure client composition over existing nodes and scroll geometry.
